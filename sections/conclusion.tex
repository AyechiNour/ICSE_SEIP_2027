\section{Conclusion and Future Work}
\label{sec:conclusion}

Locating the implementation of business rules in large systems remains a challenging task, particularly when documentation is incomplete and the relationship between business requirements and source code is not explicitly established. In this work, we presented a fully automated approach that assists developers in this task by narrowing down the set of potential implementation methods.

The approach establishes links between business-rule descriptions and source code by identifying business entities associated with the concepts expressed in each rule. These entities are then used to identify methods that manipulate or access them, resulting in a set of candidate methods for further investigation. We also use information from the documentation to refine the candidate methods and further narrow the candidate sets.

The evaluation conducted on a large industrial software system shows that the approach retains the reference implementation for most of the evaluated business rules while considerably reducing the number of candidate methods and, consequently, the Recovery Effort Index. These findings demonstrate the potential of combining semantic information from business-rule descriptions with information extracted from source code and documentation to support business-rule localization in legacy systems.

The approach is not intended to automatically identify a unique implementation of a business rule. Instead, it aims to provide developers with a focused and manageable set of candidate methods, thereby facilitating the investigation of large codebases. Several directions can be explored to further improve the approach and evaluate its practical usefulness.

First, the current evaluation is based on a single industrial system and a dataset of 100 business rules. Evaluating the approach on additional industrial systems from different domains would provide stronger evidence regarding its generalizability and applicability to systems with different architectures, naming conventions, and documentation practices.

Second, future work could validate the relationship between the Recovery Effort Index (REI) and the actual effort required by developers to locate a business rule implementation. A controlled developer study could compare the time required to complete localization tasks, the number of code elements inspected, and the perceived cognitive effort, with and without the support of our approach. This would help assess whether the reduction in candidate methods reflected by the REI translates into tangible benefits for software maintenance and provide empirical evidence to support the interpretation of this metric.

Finally, future work could investigate ranking the retained candidate methods according to their likelihood of implementing the business rule. While the current approach deliberately preserves multiple candidates to avoid discarding relevant implementations, a ranking mechanism could help developers prioritize their investigation. Additional information from source code, business-rule descriptions, and documentation could also be exploited to improve this ranking. This would extend the approach beyond search-space reduction toward more precise and developer-oriented business-rule localization.

\paragraph{Artifact Availability.}\noindent

A replication package cannot be publicly released because the evaluation relies on proprietary industrial source code and associated business-rule documentation that are subject to confidentiality restrictions.
