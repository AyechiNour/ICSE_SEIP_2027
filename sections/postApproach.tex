\section{Business-Rule Documentation as Filtering Context (RQ2)}
\label{sec:useDocumentation}

The approach described in the previous section identifies a set of candidate methods that may implement a given business rule. Although this filtering substantially reduces the initial search space, the resulting set may still contain a relatively large number of methods. The business-rule documentation provides additional information that can be exploited to further refine these candidates.

In particular, the organization of the documentation provides contextual information about the functional area or business concept associated with a rule. As described in Section~\ref{sec:industrialContext}, each documentation file has a meaningful title and is organized into sections that also provide meaningful contextual information. These elements can therefore provide additional clues about the classes in which the rule may be implemented.

We use this information as an additional filtering criterion after applying the main approach. Rather than reconsidering the complete source code, we focus only on the candidate methods produced by the approach and examine the classes in which these methods are implemented. The objective is to determine whether the class containing a candidate method is related to the context identified from the business-rule documentation.

More specifically, we extract the context information available in the documentation, namely the file title and the section title associated with the business rule. We then compare these titles with the names of the classes containing the candidate methods. A candidate method is retained when the name of its containing class contains a term corresponding to the identified documentation context. Otherwise, the method is removed from the candidate set.

For example, consider a business rule documented in a file entitled \texttt{Budget}. The title provides an indication that the rule is related to the \texttt{Budget} business concept. If a candidate method is implemented in a class such as \texttt{BudgetService} or \texttt{BudgetMethod}, the class name is consistent with this context, and the method can therefore be retained. Conversely, a candidate method implemented in a class whose name does not reflect the identified context can be discarded.

This filtering step is applied to the candidate methods obtained from the main approach. It therefore acts as a post-processing step rather than as an independent localization technique. The main approach remains responsible for identifying methods that are potentially related to the business entities and terms expressed in the rule, while the documentation provides additional contextual information to further distinguish among these candidates.

This strategy is particularly relevant to our approach because the main filtering process deliberately favors recall over precision. By retaining several candidates through the OR-based filtering strategy, we reduce the risk of discarding the actual implementation method, but some unrelated methods may remain in the resulting set. Documentation-based context provides an additional source of information that can be used to remove some of these remaining candidates without changing the initial filtering strategy.
